# PG가 느려지면 왜 우리 서비스까지 느려질까: 서킷 브레이커를 켜고 나서 알게 된 것

> ad-commerce-lab 개발 기록 1편. 코드와 실험 스크립트는 [저장소](https://github.com/HYUNWOOL/ad-commerce-lab)에 있다.

결제 대행사(PG)가 느려지는 날이면 결제와 상관없는 화면까지 같이 느려지는 일을 몇 번 겪었다. 원인은 매번 비슷했다. PG 응답을 기다리는 동안 요청 스레드와 DB 커넥션이 묶이고, 묶인 자원이 다른 요청까지 막는다. 이런 일이 생기면 회의에서 "서킷 브레이커를 달자"는 말이 쉽게 나온다. 그런데 달고 나면 무엇이 좋아지고 무엇을 잃는지 숫자로 확인해 본 적은 없었다.

그래서 가상의 광고 플랫폼을 만들고 PG를 일부러 망가뜨려 봤다. 서킷 브레이커를 켜자 장애 중에 PG로 간 승인 요청은 79건에서 21건으로 줄었다. 그런데 1분짜리 장애에 주문 300건 중 292건이 취소됐다. 이 글은 그 숫자가 나온 과정과, 그다음에 바꾼 것에 대한 기록이다.

## 실험 무대

파트너(광고주)가 광고 상품을 사면 결제를 거쳐 캠페인이 켜지는 구조다.

```
파트너 → gateway → campaign ─(Kafka: 주문 생성)→ payment → PG
                      ↑                              │
                      └──(Kafka: 결제 결과)──────────┘
```

- 주문 API는 주문을 저장하고 202를 돌려준다. 결제는 Kafka 이벤트를 받은 payment 서비스가 따로 한다.
- 상태 변경과 이벤트 발행은 Transactional Outbox로 묶었고, 받는 쪽은 Inbox로 중복을 거른다.
- PG 호출은 DB 트랜잭션 밖에서 한다. PG를 기다리는 동안 DB 커넥션을 붙잡지 않기 위해서다.

장애는 [Toxiproxy](https://github.com/Shopify/toxiproxy)로 넣었다. 서비스 사이 링크(campaign → catalog, payment → PG)마다 프록시를 두고 응답을 늦추거나 데이터를 버린다. 가짜 PG에는 요청 일부에 503을 돌려주는 스위치를 달았다. 부하는 [k6](https://k6.io)로 만들고, 같은 실험을 설정만 바꿔 여러 번 돌렸다. 숫자는 노트북 한 대의 Docker에서 잰 것이라 절대값보다 설정 사이의 차이를 보면 된다.

```bash
bash scripts/experiments/m2.sh s6 off|on        # catalog 지연 3초
bash scripts/experiments/m2.sh s4 off|fail|on   # PG 지연 2.5초 + 503 50%
bash scripts/experiments/m2.sh s5               # PG 응답을 못 받는 경우
```

## 1. 먼저, 번지는 장면부터

PG 실험 전에 "번짐"이 실제로 어떻게 생기는지부터 확인했다. 주문 API는 상품 서비스(catalog)에서 단가를 동기로 받아 온다. 이 링크를 3초씩 늦추고, campaign 서비스의 요청 스레드를 40개로 줄인 뒤(적은 부하로 재현하려고) 주문과 조회를 초당 20건씩 보냈다. 조회 API(`GET /campaigns`)는 catalog를 부르지 않는다.

| | 타임아웃 30초, 서킷 없음 | 타임아웃 1초 + 서킷 |
| --- | --- | --- |
| 조회 API p95 | 10,001ms(오류 37%) | 27ms(오류 0%) |
| 주문 API p95 | 10,001ms(오류 57%) | 5ms(전부 즉시 503) |
| campaign 요청 스레드 사용 | 40 / 40 | 4 / 40 |

catalog를 기다리는 주문 요청이 스레드 40개를 모두 붙잡자, catalog와 상관없는 조회 API까지 스레드를 얻지 못해 10초씩 기다리다 실패했다. 현업에서 본 장면이 그대로 나왔다. 타임아웃을 1초로 줄이고 서킷을 달자 처음 몇 건만 1초를 기다린 뒤 서킷이 열렸고, 조회 API는 장애가 없을 때와 같았다.

물론 공짜는 아니다. catalog가 아픈 동안 주문은 하나도 받지 못했다(즉시 503과 Retry-After). 보호가 없을 때는 주문의 43%가 결국 들어갔다. 오래된 가격 캐시로 주문을 받는 방법도 있지만, 바뀐 단가로 결제될 수 있어 돈이 걸린 경로에는 쓰지 않기로 했다.

## 2. 결제를 비동기로 떼어 놓으니 API는 멀쩡했다

PG는 catalog와 다르게 처음부터 Kafka 뒤에 두었다. 이번에는 payment와 PG 사이 응답을 2.5초씩 늦추고 요청의 절반에 503을 돌려주게 한 뒤, 주문을 초당 5건, 캠페인 조회를 초당 20건씩 60초 동안 보냈다. 보호 없음, 서킷 + 바로 실패, 서킷 + 보류 세 가지로 돌렸다.

보호 장치를 하나도 켜지 않은 첫 실행에서 주문 API의 p95는 31ms, 조회 API는 16ms였다. PG가 2.5초씩 느린데도 파트너가 보는 API는 영향을 받지 않았다. 주문 API는 PG를 부르지 않고 Kafka에 이벤트만 남기기 때문이다. "PG가 느리면 우리 서비스도 느려진다"는 문제의 상당 부분은 서킷 브레이커가 아니라 이 비동기 경계가 막았다.

대신 문제는 안쪽으로 옮겨 갔다.

| 보호 없음 | 값 |
| --- | --- |
| 장애 중(60초) PG가 받은 승인 요청 | 79건 |
| 결제가 확정되기까지 p50 / p95 / 최대 | 30.6초 / 59.0초 / 68.0초 |
| 결제 컨슈머에 밀린 메시지(최대) | 253건 |

컨슈머 3개가 2.5초짜리 PG 호출을 하나씩 붙잡고 있으니 초당 1.2건밖에 처리하지 못했다. 들어오는 주문은 초당 5건이라 그 차이만큼 Kafka에 메시지가 쌓였다. 파트너는 1분 넘게 "결제 확인 중"을 봐야 했고, 아픈 PG는 쉬지 못하고 계속 요청을 받았다. 장애가 1분이 아니라 10분이었다면 밀린 메시지는 초당 3.8건씩 계속 늘었을 것이다.

그나마 PG를 두드린 양이 79건에서 그친 건 컨슈머가 3개뿐이어서다. 같은 일을 요청 스레드 수백 개에서 동기로 했다면 아픈 PG에 훨씬 많은 요청이 몰렸을 것이다.

## 3. 서킷 브레이커를 켰더니 PG는 살았고 주문은 죽었다

서킷 브레이커(Resilience4j)는 최근 20건 중 실패나 2초 넘는 느린 호출이 절반을 넘으면 열리게 했다. 열려 있는 10초 동안은 PG를 부르지 않고 바로 실패를 돌려준다.

| | 보호 없음 | 서킷 + 바로 실패 |
| --- | --- | --- |
| 장애 중 PG가 받은 승인 요청 | 79건 | 21건 |
| 결제 확정 p50 / p95 | 30.6초 / 59.0초 | 0.3초 / 6.7초 |
| 밀린 메시지(최대) | 253건 | 41건 |
| 결제 성공 | 301건 | **8건** |

PG 부하와 대기 시간은 기대한 만큼 줄었다. 그런데 결과 표를 보고 한동안 멈췄다. 1분 동안 PG가 아팠을 뿐인데 주문 292건이 PG_UNAVAILABLE로 취소됐다. 파트너 입장에서는 광고를 사려다 실패했고, 다시 주문해야 한다.

돌아보면 서킷 브레이커가 한 일은 "PG를 부르지 않는다"까지였다. 부르지 않은 결제를 실패로 끝낸 건 내가 짠 코드였다. 서킷이 열렸을 때 무엇을 할지는 라이브러리 설정이 아니라 업무 결정이었다.

## 4. 열렸을 때는 실패 대신 보류

광고 구매는 몇 분 늦어도 되는 결제다. 그리고 서킷이 열려 부르지 않은 결제나 PG가 503으로 거절한 결제는 PG가 처리하지 않았다는 게 확실하다. 그러면 나중에 다시 보내도 안전하다. 그래서 이렇게 바꿨다([ADR-0006](../docs/02-design/adr/0006-defer-when-pg-unavailable.md)).

1. PG가 받지 않은 결제는 REQUESTED 상태로 두고 사유만 남긴다. 주문은 "결제 확인 중"에 머문다.
2. 5초마다 도는 재조회 작업이 15초 지난 보류 결제를 집는다. PG에 결제 ID로 조회하고, 없으면 같은 멱등키로 승인을 다시 보낸다. 서킷이 아직 열려 있으면 PG를 부르지 않고 다음 회차로 넘긴다.
3. 결제를 만든 지 10분이 지났는데 PG에도 없으면 그때 실패로 확정한다.

| | 보호 없음 | 서킷 + 바로 실패 | 서킷 + 보류 |
| --- | --- | --- | --- |
| 장애 중 PG가 받은 승인 요청 | 79건 | 21건 | 21건 |
| 결제 확정 p50 / p95 | 30.6초 / 59.0초 | 0.3초 / 6.7초 | 39.3초 / 65.9초 |
| 밀린 메시지(최대) | 253건 | 41건 | 33건 |
| 결제 성공 | 301건 | 8건 | 300건 |

보류로 바꾸자 아픈 PG에 보낸 요청은 바로 실패와 같은 21건이었고, Kafka에 밀린 메시지도 33건에서 멈췄다. 그리고 주문을 하나도 잃지 않았다. 장애가 끝나자 재조회가 보류된 결제 288건을 같은 멱등키로 다시 보냈고, 모두 승인됐다.

대신 기다림이 늘었다. 결제가 확정되기까지 p50이 39.3초로, 보호 없음(30.6초)보다 오히려 9초 길다. 보류된 결제는 장애가 끝나도 바로 다시 나가지 않는다. 재조회가 집을 때까지 15초를 기다리고, 서킷이 반열림으로 바뀌어 PG가 괜찮은지 확인할 때까지 또 기다린다. 이 대기는 줄일 수 있지만, 줄일수록 PG가 회복되자마자 몰려가는 요청이 많아진다. 1분짜리 장애에서는 보호 없음이 조금 더 빨랐다. 장애가 길어지면 보호 없음은 밀린 메시지가 계속 늘고, 보류는 서킷이 막는 동안 PG를 부르지 않으니 컨슈머가 밀리지 않을 것이다. 다만 이건 계산이고 긴 장애는 아직 재 보지 않았다.

## 5. 타임아웃은 실패가 아니다

PG 호출이 타임아웃되면 PG에서는 승인됐을 수도 있다. 이걸 실패로 처리하면 카드에서는 돈이 빠졌는데 캠페인은 취소되는 일이 생긴다. 그래서 타임아웃은 UNKNOWN으로 두고, 재조회가 PG에 물어 확정하게 했다.

가짜 PG가 3.5초 뒤에 승인하게 하고(우리 쪽 타임아웃은 3초) 주문 8건을 넣었다. 8건 모두 UNKNOWN이 됐다가 재조회로 승인 확정됐고, PG가 받은 승인 요청도 8건 그대로였다. 사람이 볼 일은 없었다.

다만 처음 돌렸을 때는 확정까지 p50 22.8초가 걸렸다. 로그를 보니 재조회가 "PG에 물어보지 못함"으로 두 번씩 넘어가고 있었다. 승인과 조회가 서킷 브레이커 하나를 같이 쓰고 있었던 게 원인이었다. 승인 타임아웃 8건이 서킷을 열었고, 열린 서킷이 그 8건의 결과를 확인할 조회까지 10초 동안 막았다. 승인은 카드사까지 다녀오고 조회는 PG 안에서 끝나니, 둘이 아픈 시점은 다를 수 있다. 서킷을 둘로 나누자 p50은 12.8초가 됐고 모두 첫 재조회에서 끝났다.

PG로 가는 요청 자체가 닿지 않는 경우(연결은 열렸는데 데이터가 버려지는 상황을 20초 동안)도 넣어 봤다. 결제 4건이 UNKNOWN으로 기다리다가, 장애가 풀린 뒤 첫 재조회에서 "PG에 없음"을 확인하고 같은 멱등키로 다시 보내 승인됐다. PG에 기록된 결제는 4건이었다. 결제 ID를 멱등키로 쓰니 몇 번을 다시 보내도 결제마다 하나다.

## 6. 안 보이던 것들

요청 하나가 서비스 다섯 개를 지나가니 로그만으로는 따라가기 어려웠다. OpenTelemetry로 트레이스를 붙였더니(Spring Boot 4의 `spring-boot-starter-opentelemetry`) 주문 하나가 gateway → campaign → catalog → Kafka → payment → PG → Kafka → campaign까지 한 트레이스로 보였다. 그 과정에서 두 가지를 배웠다.

**Outbox에서 트레이스가 끊긴다.** Outbox 릴레이는 스케줄러 스레드에서 돌아서, 원래 요청의 트레이스 문맥을 모른다. 그래서 Outbox 행을 쓸 때 현재 `traceparent`를 같이 저장하고, 릴레이가 그 문맥 안에서 Kafka로 보내게 했다. 이렇게 해야 트레이스에 "Outbox에서 기다린 시간"까지 찍힌다. 주문 저장부터 발행까지 130ms쯤 비는 구간이 바로 릴레이 주기(200ms)다.

**Kafka 클라이언트의 lag 지표는 0이었다.** 보호 없음 실험에서 메시지가 253건 밀렸는데, 컨슈머가 내보내는 `records-lag` 지표는 계속 0이었다. 이 값은 "아직 가져오지 않은" 메시지만 센다. 컨슈머가 수백 건을 한 번에 가져가 붙잡고 느리게 처리하는 동안에는 밀린 게 하나도 없는 것처럼 보인다. 처리 지연은 브로커 쪽 커밋 오프셋으로 봐야 했다.

## 정리

이번에 확인한 것을 줄이면 이렇다.

- 외부 장애가 API까지 번지는 건 동기 호출이 요청 스레드를 붙잡기 때문이다. catalog가 3초 늦어지자 catalog와 무관한 조회 API까지 p95 10초가 됐고, 타임아웃 1초와 서킷으로 27ms로 돌아왔다.
- 결제를 Kafka 뒤로 보내자 PG가 아파도 주문·조회 API는 그대로였다.
- 서킷 브레이커는 아픈 PG를 더 두드리지 않게 해 준다. 하지만 열렸을 때 결제를 어떻게 처리할지는 따로 정해야 한다. 이번에는 바로 실패에서 보류 후 재시도로 바꿨다.
- 타임아웃은 "모름"이다. 멱등키와 재조회가 있으면 사람이 확인하지 않아도 돈이 어긋나지 않게 확정할 수 있다.
- 서킷 브레이커 하나를 여러 호출이 같이 쓰면, 한쪽의 실패가 다른 쪽을 막는다.

아직 해 보지 못한 것도 있다. 실험은 노트북 한 대의 Docker에서 돌렸고, 장애는 1분짜리 하나뿐이다. 장애가 10분을 넘기면 보류한 결제가 기한에 걸려 한꺼번에 취소되는데, 그때 파트너에게 무엇을 보여 줄지는 아직 정하지 않았다.

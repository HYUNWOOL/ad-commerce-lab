# 노출 이벤트 초당 1만 건, 예산을 넘기지 않고 과금하기

> ad-commerce-lab 개발 기록 2편. [1편](01-when-pg-slows-down.md)에서 광고 상품을 결제하는 부분을 만들었다. 이번에는 결제한 예산이 노출마다 실제로 쓰이는 부분이다. 코드와 실험 스크립트는 [저장소](https://github.com/HYUNWOOL/ad-commerce-lab)에 있다.

광고 과금은 숫자가 크고 돈이 걸려 있다. 노출 한 건은 몇십 원이지만 초당 수천 건이 들어오고, 파트너가 정한 예산을 1원이라도 넘겨 받으면 안 된다. 같은 노출이 두 번 오기도 하고, 처리하던 서버가 죽기도 한다. 그래서 이번에 지키려 한 약속은 세 가지였다.

1. 같은 노출은 한 번만 과금한다.
2. 예산을 넘겨 과금하지 않는다.
3. 서버가 처리 도중 죽어도 1과 2가 그대로다.

결론부터 말하면 세 약속은 처음부터 지켜졌다. 대신 "정확하다"와 "제때 끝난다"가 다른 문제라는 걸 두 번 배웠다.

## 구조: 받는 곳과 돈을 계산하는 곳을 나눈다

```
광고 서버 → POST /impressions ─→ Kafka(delivery.impression) ─→ 배치 리스너 ─→ DB(예산·노출·과금 기록)
            (형식만 보고 202)                                  (최대 500건씩)       └→ Outbox → 정산 원장
```

수집 API는 노출을 Kafka에 넣고 브로커 확인을 받으면 202를 돌려준다. DB는 건드리지 않는다. 받는 속도와 계산하는 속도를 떼어 놓기 위해서다.

돈 계산은 배치 리스너가 한다. Kafka에서 한 번에 받은 메시지 묶음을 트랜잭션 하나로 처리한다.

```sql
-- 1) 처음 본 노출만 남긴다. eventId가 PK라 두 번째부터는 걸러진다.
INSERT INTO impression_events (event_id, campaign_id, placement, occurred_at)
SELECT * FROM unnest(:ids, :campaigns, :placements, :times)
ON CONFLICT (event_id) DO NOTHING
RETURNING campaign_id, occurred_at;

-- 2) 캠페인마다 남은 예산 안에서만 깎는다. 한 문장이라 사이에 끼어들 틈이 없다.
UPDATE campaign_budgets
SET spent = spent + LEAST(:n, (budget - spent) / cpv_price) * cpv_price
WHERE campaign_id = :id AND status = 'ACTIVE';
```

`LEAST`가 "남은 예산으로 살 수 있는 노출 수"보다 많이 깎지 못하게 막는다. 그래도 코드가 틀릴 수 있으니 테이블에 `CHECK (spent <= budget)`를 걸어 DB가 한 번 더 막는다. Kafka 오프셋은 이 트랜잭션이 커밋된 뒤에 커밋된다. 커밋 전에 죽으면 같은 배치를 다시 받고, 이미 넣은 노출은 1번에서 걸러진다.

## Redis는 넣지 않았다

설계 초안에는 Redis가 있었다. 노출 ID를 Redis에서 먼저 걸러 DB 부담을 줄이고, 예산도 Redis에서 깎을 생각이었다. 그런데 따져 보니 새 노출은 어차피 DB에 넣어야 최종 중복 확인이 된다. Redis가 줄여 주는 건 중복분의 DB 쓰기뿐이다. 예산을 Redis에서 깎으면 돈의 원본이 두 곳이 되고, Redis가 죽었을 때 어느 쪽이 맞는지 따로 맞춰야 한다.

그래서 먼저 DB만으로 재 보기로 했다. k6로 노출을 100건씩 묶어 초당 5,000건, 그다음 1만 건을 60초 동안 보냈다.

| | 초당 5천 건 | 초당 1만 건 |
| --- | --- | --- |
| 수집 API p95 | 11ms | 12ms |
| 과금 지연(노출 발생 → 과금) p95 | 0.33초 | 0.20초 |
| 부하가 끝난 뒤 과금이 따라잡기까지 | 2초 | 2초 |
| 과금 정확도 | 차이 0 | 차이 0 |

목표(초당 5천 건, 과금 지연 p95 2초)를 넘었다. 노트북 한 대의 Docker에서 잰 숫자라 운영 환경과 같지는 않겠지만, 적어도 이 규모에서 Redis를 넣을 이유는 찾지 못했다.

## 과금은 따라갔는데 정산이 2분 늦었다

첫 실행에서 과금 자체는 부하와 함께 끝났다. 그런데 정산 원장의 숫자가 과금 숫자를 따라잡는 데 부하가 끝나고도 148초가 걸렸다.

원인은 과금 이벤트 수였다. 노출 30만 건을 과금하면서 `CampaignCharged` 이벤트가 31,804건 나갔다. 노출 9.4건마다 하나다. 컨슈머가 메시지가 들어오는 대로 몇십 건씩 가져가 배치가 작았고, 배치마다 캠페인마다 이벤트를 하나씩 냈기 때문이다.

이 이벤트를 Kafka로 옮기는 Outbox 릴레이도 느렸다. 같은 캠페인의 이벤트 순서를 지키려고 한 건씩 보내고 확인을 기다렸는데, 그러면 초당 약 160건이 한계였다. 3만 건을 보내는 데 196초가 걸렸다.

두 가지를 바꿨다.

- 컨슈머가 최대 500ms까지 기다려 배치를 채우게 했다(`fetch.min.bytes 128KB`, `fetch.max.wait.ms 500`). 설계 초안의 "1초 창 집계"를 버퍼나 타이머 없이 Kafka 설정으로 한 셈이다.
- 릴레이는 묶음을 한꺼번에 보내고 모두 확인되면 표시한다. Kafka의 멱등 프로듀서는 같은 파티션 안의 순서를 지켜 주므로, 같은 키(캠페인)의 순서는 그대로다.

| | 바꾸기 전 | 바꾼 뒤 |
| --- | --- | --- |
| 과금 이벤트 | 31,804건(노출 9.4건당 1건) | 3,478건(86건당 1건) |
| 원장이 따라잡기까지 | 148초 | 5초 |
| 과금 지연 p95 | 54ms | 327ms |

대가는 과금 지연이다. 배치를 채우려고 기다리는 만큼 p95가 54ms에서 327ms로 늘었다. 예산이 다 됐다는 판단도 그만큼 늦지만, 예산을 넘겨 깎는 일은 `LEAST`가 막으니 돈이 틀리지는 않는다. 두 가지를 한 번에 바꿔서 각각이 얼마나 기여했는지는 나눠 재지 못했다.

## 예산 10만 원 캠페인에 노출 9만 건

예산 10만 원, 노출 2,000건까지만 살 수 있는 캠페인에 전체 노출의 30%를 몰아줬다. 초당 1,500건이 들어오니 2초도 안 돼 예산이 바닥난다.

| 항목 | 결과 |
| --- | --- |
| 받은 노출 | 89,491건 |
| 과금한 노출 / 사용액 | 2,000건 / 100,000원 |
| 예산 소진 이벤트 | 1건 |
| 캠페인 서비스 화면 | EXHAUSTED, 사용액 100,000원 |

예산 소진 이벤트(`BudgetExhausted`)가 한 번만 나가는 것도 같은 UPDATE 덕분이다. `WHERE status = 'ACTIVE'`로 집은 행이 이번 UPDATE에서 EXHAUSTED로 바뀌었을 때만 이벤트를 낸다. 이미 소진된 캠페인은 행이 잡히지 않는다.

## 처리 도중 서버를 죽였다

노출의 20%를 이미 보낸 ID로 다시 보내면서, 20초에 delivery 서비스를 SIGKILL로 죽이고 바로 다시 띄웠다. 수집 API도 같이 죽으므로, 광고 서버 역할을 하는 k6는 202를 못 받은 요청을 같은 본문으로 다시 보낸다.

과금은 정확했다. 처음 본 노출 235,440건, 과금한 노출 235,440건. 재전송 53,660건과 실패 뒤 다시 보낸 요청 714건이 모두 걸러졌다.

그런데 과금 지연 p50이 21초였다. 로그를 보니 앱은 죽은 뒤 4초 만에 다시 떴는데, Kafka 파티션을 다시 받은 건 그로부터 39초 뒤였다. 컨슈머 그룹은 죽은 멤버가 정말 죽었는지 세션 타임아웃(기본 45초)이 지날 때까지 기다린다. 그동안 그 파티션은 아무도 처리하지 않는다.

정적 멤버십(`group.instance.id`)을 켜서 해결했다. 같은 이름으로 다시 들어온 멤버는 기다림 없이 자기 파티션을 돌려받는다.

| | 정적 멤버십 없음 | 정적 멤버십 |
| --- | --- | --- |
| 앱이 뜬 뒤 파티션을 받기까지 | 39초 | 0.02초 |
| 과금 지연 p50 / p95 | 21초 / 30초 이상 | 0.13초 / 3.2초 |
| 과금 정확도 | 차이 0 | 차이 0 |

정확도만 봤다면 이 문제는 지나쳤을 것이다. 돈은 맞았지만 40초 동안 예산 소진을 아무도 판단하지 않았다.

## 원장은 DB가 지킨다

과금된 돈은 정산 서비스의 복식부기 원장에 들어간다. 결제가 승인되면 "PG 미수금 / 파트너 선수금", 노출이 과금되면 "파트너 선수금 / 광고 매출"로 적는다. 파트너 월 정산서(결제액, 사용액, 잔액)는 이 원장의 합계로 계산한다.

차변 합 = 대변 합은 코드에서도 확인하지만, DB에도 커밋 시점에 도는 제약 트리거를 걸었다. 코드가 한쪽 줄만 쓰는 실수를 해도 커밋되지 않는다. 원장은 UPDATE와 DELETE도 트리거로 막았다. 틀린 기록은 고치지 않고 반대 분개로 바로잡는다. 모든 실험이 끝날 때마다 원장의 선수금 사용액 합과 delivery의 사용액 합을 비교했고, 매번 같았다.

## 정리

- 중복 제거는 DB 유니크 하나로 충분했다. 예산 차감은 `LEAST`가 들어간 UPDATE 한 문장과 `CHECK` 제약으로 막았다.
- Redis는 재 보고 나서 넣지 않았다. 돈의 원본은 DB 하나다.
- 과금이 빨라도 그 결과를 받아 적는 쪽이 느리면 정산이 늦는다. 작은 배치가 이벤트를 아홉 배로 불렸다.
- 정확함과 빠름은 따로 재야 한다. 서버가 죽어도 돈은 맞았지만, 정적 멤버십 없이는 40초 동안 과금이 멈췄다.

아직 못 한 것도 있다. delivery가 하나뿐이라 인스턴스가 아예 돌아오지 않을 때 다른 인스턴스로 넘어가는 경우는 재지 않았다. 노출 기록 테이블은 계속 자라는데, 날짜별로 나눠 오래된 것을 지우는 부분도 아직 없다. 그리고 결제 이벤트에 `partnerId` 필드를 추가하면서, 이전에 쌓인 이벤트는 정산이 읽지 못하게 됐다. 필드를 추가해도 안전한 건 받는 쪽이 그 필드를 선택으로 다룰 수 있을 때뿐이었다.

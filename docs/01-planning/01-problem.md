# 1. 문제 정의

> 현업에서 반복해서 겪은 불편을 "이런 구조라면 어떨까?"라는 가설로 바꾸고, 실제로 만들어 검증해 보는 실험 프로젝트다. 회사 시스템에 바로 넣기 전에, 같은 문제를 가진 가상의 플랫폼에서 먼저 구조를 시험한다.

## 1.1 배경

8년 동안 커머스·광고·결제·정산 백엔드를 만들고 운영했다. 그중 최근 몇 년은 입점 파트너가 플랫폼 안에서 광고 상품을 사고, 노출되고, 노출 기준으로 과금·정산되는 광고형 커머스를 맡았다.

이 프로젝트의 무대는 이 경험을 일반화한 **가상의 동네 매장 예약 플랫폼 "Nearby"**다. 실제 회사의 이름, 데이터, 내부 수치는 쓰지 않는다.

| 등장인물 | 하는 일 |
| --- | --- |
| 파트너(입점 매장 사장님) | 파트너 앱에서 광고 상품을 사고, 예산과 기간을 정하고, 성과와 정산을 본다 |
| 운영 매니저(플랫폼 내부) | 환불, 정산 문의, 캠페인 중지 같은 요청을 처리한다 |
| 앱 사용자 | 광고가 노출되는 화면을 본다. 노출이 곧 과금의 근거가 된다 |

## 1.2 현업에서 겪은 불편 세 가지

### P1. 외부 PG가 느려지면 우리 서비스 전체가 같이 느려진다

- **겪은 일:** 결제 승인 호출이 외부 PG에서 오래 걸리면, 그 요청을 들고 있는 서버 스레드와 DB 커넥션이 묶인다. 그러면 결제와 상관없는 API까지 함께 느려진다.
- **더 곤란한 점:** 타임아웃이 나면 결제가 됐는지 안 됐는지 알 수 없다. 사람이 PG 관리자 화면에서 하나씩 확인해야 했다.
- **지금 방식의 한계:** 타임아웃 숫자를 조정하는 정도로 대응했다. 장애가 퍼지는 경로 자체는 그대로였다.

### P2. 화면 문구 하나 바꾸는데 앱 배포를 기다려야 한다

- **겪은 일:** 광고 상품 구매 화면의 문구, 구성, 노출 순서를 바꾸려면 AOS·iOS를 각각 배포하고 스토어 심사를 기다려야 했다. 크로스펑셔널 스쿼드에서 이 대기가 일정 병목이었다.
- **더 곤란한 점:** 업데이트하지 않은 구버전 앱 사용자에게는 끝까지 반영되지 않는다. 그래서 정책(예: 환불 안내 문구)이 사용자마다 다르게 보인다.
- **지금 방식의 한계:** 원격 설정(feature flag)으로 일부 값만 바꿀 수 있었고, 화면 구조는 바꿀 수 없었다.

### P3. 운영·CS 요청이 결국 개발자에게 온다

- **겪은 일:** 환불 처리, 정산 내역 확인, 캠페인 강제 중지 같은 요청이 운영 도구로 해결되지 않으면 개발자가 직접 처리했다. 셀프서비스 기능을 하나씩 만들어 줄여 왔지만, 요청 유형이 계속 늘었다.
- **더 곤란한 점:** 운영자에게 DB나 강한 관리자 권한을 주면 빠르지만, 금액을 잘못 건드릴 위험이 커진다.
- **지금 방식의 한계:** 요청 유형마다 백오피스 화면을 따로 만들었다. 만드는 속도가 요청이 늘어나는 속도를 못 따라갔다.

### 함께 다루는 실무 경험: 노출 데이터 급증

불편이라기보다 실무에서 직접 다뤄 본 문제다. 노출 기준 과금(CPV)으로 바꾸면서 노출 이벤트가 크게 늘었다. 그래서 과금·정산 연산을 서비스 서버에서 떼어 내야 했다. 이 프로젝트에서는 같은 문제를 Kafka 기반 파이프라인으로 다시 풀어 본다.

## 1.3 가설과 검증 기준

| 불편 | 가설: 이런 구조라면 어떨까? | 검증 기준(검증 단계에서 실측) |
| --- | --- | --- |
| P1 | 서비스를 나누고, 결제는 Kafka로 비동기화하고, 동기 호출에는 서킷 브레이커·타임아웃·벌크헤드를 두면 PG 장애가 결제 서비스 안에 갇힌다. 결과를 모르는 건은 자동 재조회로 확정한다 | PG가 3초 지연·50% 실패할 때, 결제와 무관한 API의 p99가 평시 대비 크게 나빠지지 않는다. 결과 불명 건의 수동 확인 0건 |
| P2 | 파트너 앱 화면을 서버가 내려주는 SDUI로 만들면 문구·구성·순서를 앱 배포 없이 바꿀 수 있다. 하위 서비스가 죽어도 해당 영역만 대체 화면으로 바뀐다 | 화면 변경이 배포 없이 반영된다. 구버전 클라이언트가 모르는 컴포넌트를 받아도 화면이 깨지지 않는다. 하위 서비스 장애 시 다른 영역은 정상 표시 |
| P3 | 운영 기능을 AI 에이전트가 쓰는 도구(MCP)로 열고, 금액·권한·한도 판단은 서버 정책 코드가 하면 운영 요청을 자연어로 처리하면서도 돈은 틀리지 않는다 | 정책 위반 실행 0건(프롬프트 인젝션 평가 포함). 고위험 작업은 100% 사람 승인 후 실행. 같은 요청을 여러 번 보내도 실행 1번 |
| 노출 급증 | 노출 이벤트를 Kafka로 받고 캠페인 기준으로 파티션을 나눠 집계하면, 많은 이벤트에서도 예산을 넘겨 과금하지 않는다 | 부하 실험에서 예산 초과 과금 0원, 처리량과 지연 기록 |

## 1.4 이 프로젝트가 아닌 것

- 실제 회사 시스템의 재현이 아니다. 가상의 플랫폼에서 구조를 시험한다.
- 운영 서비스가 아니다. 장애를 주입하고 숫자를 재는 실험 환경이다.
- 가설이 틀릴 수 있다. 틀린 결과도 검증 문서에 그대로 남긴다.

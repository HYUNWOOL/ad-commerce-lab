# 3. 요구사항

번호는 설계·개발·검증 문서에서 그대로 참조한다.

## 3.1 기능 요구사항

### 광고 상품·주문 (FR-1xx)

| ID | 요구사항 |
| --- | --- |
| FR-101 | 광고 상품(지면, 기간, CPV 단가, 최소 예산)을 조회할 수 있다 |
| FR-102 | 파트너는 상품·기간·예산을 정해 광고 주문을 만든다. 같은 Idempotency-Key로 다시 요청하면 같은 주문을 돌려준다 |
| FR-103 | 주문은 상태 머신을 따른다: 생성 → 결제 대기 → 결제 완료 → 캠페인 활성 / 결제 실패 → 취소 |
| FR-104 | 결제가 실패하면 주문을 취소하는 보상 처리를 한다 |
| FR-105 | 활성 캠페인은 중지·재개·환불 요청을 받을 수 있다 |

### 결제 (FR-2xx)

| ID | 요구사항 |
| --- | --- |
| FR-201 | 결제 승인·취소(환불)를 외부 PG로 요청한다 |
| FR-202 | PG 호출 결과를 모르면 "확인 중" 상태로 두고, 재조회로 확정한다 |
| FR-203 | 같은 주문에 결제가 두 번 승인되지 않는다 |
| FR-204 | 부분 환불을 지원한다. 환불 가능 금액은 서버가 계산한다(쓴 만큼 제외) |

### 노출·과금 (FR-3xx)

| ID | 요구사항 |
| --- | --- |
| FR-301 | 노출 이벤트를 받는다(캠페인, 지면, 시각, 이벤트 ID) |
| FR-302 | 같은 이벤트 ID는 한 번만 과금한다 |
| FR-303 | 캠페인별로 노출을 집계해 CPV 단가만큼 예산을 차감한다 |
| FR-304 | 예산을 넘겨 과금하지 않는다. 예산이 소진되면 캠페인을 멈추는 이벤트를 낸다 |

### 정산 (FR-4xx)

| ID | 요구사항 |
| --- | --- |
| FR-401 | 결제·과금·환불을 원장에 기록한다(차변 합 = 대변 합) |
| FR-402 | 파트너별 기간 정산서(결제액, 사용액, 환불액, 잔액)를 만든다 |
| FR-403 | 같은 이벤트를 두 번 받아도 원장은 한 번만 기록한다 |

### 서버 주도 화면 (FR-5xx)

| ID | 요구사항 |
| --- | --- |
| FR-501 | 파트너 앱의 화면(홈, 광고 상품 목록·상세·구매, 캠페인 성과, 승인 요청)을 서버가 JSON 스키마로 내려준다 |
| FR-502 | 운영 콘솔의 화면(환불 처리, 정산 조회, 승인 대기 목록)도 같은 방식으로 내려준다 |
| FR-503 | 화면 구성(섹션 순서, 문구, 노출 여부)은 배포 없이 설정으로 바꾼다 |
| FR-504 | 클라이언트는 자신이 아는 컴포넌트 버전을 알려 주고, 서버는 그에 맞춰 내려준다. 모르는 컴포넌트는 대체 표시로 그린다 |
| FR-505 | 화면을 이루는 하위 서비스 하나가 실패해도 그 영역만 대체 표시하고 나머지는 그린다 |

### AI 에이전트 (FR-6xx)

| ID | 요구사항 |
| --- | --- |
| FR-601 | 에이전트용 도구를 MCP 서버로 제공한다. 파트너용(상품 조회, 추천, 구매, 캠페인 조회)과 운영용(환불 요청, 정산 조회, 캠페인 중지)으로 나눈다 |
| FR-602 | 파트너는 에이전트에게 위임 한도(1회 한도, 기간 한도, 허용 상품, 만료일)를 준다. 서버가 매 호출마다 검사한다 |
| FR-603 | 한도를 넘거나 고위험인 작업은 `APPROVAL_REQUIRED`를 돌려주고 승인 요청을 만든다. 사람이 승인 화면에서 승인해야 실행된다 |
| FR-604 | 도구 호출마다 Idempotency-Key를 쓴다. 재시도해도 한 번만 실행된다 |
| FR-605 | 모든 도구 호출(요청자, 입력, 정책 판단, 결과)을 감사 로그로 남긴다 |

## 3.2 비기능 요구사항

| ID | 분류 | 요구사항 |
| --- | --- | --- |
| NFR-1 | 정합성 | 돈은 원 단위 정수로만 다룬다. 결제·과금·원장 어디서도 중복 처리가 없다 |
| NFR-2 | 장애 격리 | 서비스 사이 동기 호출에는 타임아웃·서킷 브레이커·재시도 정책이 있다. 외부 PG 장애가 결제 서비스 밖으로 번지지 않는다 |
| NFR-3 | 데이터 소유 | 서비스마다 자기 DB를 가진다. 다른 서비스의 DB를 직접 읽지 않는다 |
| NFR-4 | 이벤트 전달 | 상태 변경과 이벤트 발행이 어긋나지 않는다(Transactional Outbox). 소비는 멱등이다(Inbox) |
| NFR-5 | 성능 | 노출 이벤트 수집의 처리량과 지연 목표를 검증 단계에서 정하고 잰다 |
| NFR-6 | 관측 | 요청 하나를 서비스 경계를 넘어 추적할 수 있다(분산 트레이싱). 서킷 상태, 컨슈머 지연, 오류율을 대시보드로 본다 |
| NFR-7 | 재현성 | `docker compose up` 한 번으로 전체를 띄운다. 장애 주입과 부하 실험은 스크립트 한 줄로 재현한다 |
| NFR-8 | 보안 | API 키 기반 인증, 운영 기능은 역할 확인. 시크릿은 저장소에 두지 않는다 |
| NFR-9 | 테스트 | 서비스마다 단위 테스트와, 실제 Postgres·Kafka에 붙는 통합 테스트가 있다 |

## 3.3 성공 지표 (가설 검증)

| 가설 | 지표 | 판정 |
| --- | --- | --- |
| P1 | PG 장애 중 비결제 API p99, 결과 불명 건 수동 확인 수 | 전후 비교 숫자를 검증 문서에 기록 |
| P2 | 배포 없이 바뀐 화면 수, 구버전 클라이언트 오류 수, 부분 장애 시 정상 영역 비율 | 시나리오 S10~S12 통과 |
| P3 | 정책 위반 실행 수, 승인 없이 실행된 고위험 작업 수, 인젝션 평가 통과율 | 0건, 0건, 평가셋 전부 통과 |
| 노출 급증 | 초당 처리량, p99 지연, 예산 초과 과금액 | 숫자 기록, 초과 과금 0원 |

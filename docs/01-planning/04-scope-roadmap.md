# 4. 범위와 로드맵

## 4.1 시스템 경계 (개략)

서비스를 업무 경계로 나눈 MSA로 만든다. 서비스 사이는 두 가지 방식으로만 대화한다.

- **비동기(Kafka 이벤트):** 상태가 바뀌었음을 알린다. 주문 → 결제 → 캠페인 활성화 → 과금 → 정산이 이벤트로 이어진다(코레오그래피 Saga).
- **동기(HTTP + 서킷 브레이커):** 지금 바로 답이 필요한 조회에만 쓴다. 호출하는 쪽이 타임아웃·서킷 브레이커·대체 응답을 책임진다.

| 서비스 | 맡는 업무 | 주로 쓰는 통신 |
| --- | --- | --- |
| gateway | 진입점, 인증, 라우팅, 경로별 서킷 브레이커·요청 제한 | 동기 |
| catalog | 광고 상품·지면·단가 | 동기(조회 제공) |
| campaign | 광고 주문·캠페인 상태 머신, 예산·기간 | 동기 호출(catalog), Kafka 발행·소비 |
| payment | 결제 승인·취소, PG 장애 격리, 결과 재조회 | Kafka, 외부 PG 동기 호출 |
| delivery | 노출 수집·집계·과금, 예산 차감 | Kafka 대량 처리 |
| settlement | 원장, 정산서 | Kafka 소비 |
| experience | 파트너 앱·운영 콘솔 화면 스키마(SDUI BFF) | 여러 서비스 동기 호출 + 영역별 대체 표시 |
| agent | AI 에이전트용 MCP 도구, 위임 한도·승인, 감사 로그 | gateway 동기 호출 |
| mock-pg | 가짜 외부 PG(지연·실패 설정, 결과 조회, 정산 파일) | — |
| web | 파트너 앱·운영 콘솔 SDUI 렌더러 | experience 호출 |

구체적인 API·이벤트·DB는 설계 단계(docs/02-design)에서 정한다.

## 4.2 범위

| 포함 | 제외 |
| --- | --- |
| 위 서비스 전부, Kafka·Postgres(Redis는 S7 실측 뒤 넣지 않기로 함, ADR-0007) | 실제 PG 연동, 실제 카드 정보 |
| 장애 주입(Toxiproxy), 부하 실험(k6) | 쿠버네티스, 멀티 리전, 서비스 메시 |
| 분산 트레이싱·지표 대시보드 | 회원가입·로그인(정적 API 키로 대신) |
| 파트너 앱·운영 콘솔 웹 화면(SDUI) | 네이티브 앱(웹 렌더러로 같은 원리를 보인다) |
| AI 에이전트 MCP 도구와 평가 | 상시 클라우드 배포(로컬 실행 + 녹화 + 결과 숫자) |

## 4.3 로드맵 (6주)

| 주차 | 단계 | 내용 | 완료 기준 | 블로그 |
| --- | --- | --- | --- | --- |
| W0 | 기획·설계 | 문제 정의, 시나리오, 요구사항, 아키텍처, 도메인·이벤트·API 명세, ADR, GitHub Milestone·Issue | 설계 문서와 이슈 목록 | — |
| W1 | M1 구매·결제 코어 | catalog, campaign, payment, mock-pg, gateway. 멱등키, 상태 머신, Outbox → Kafka, 코레오그래피 Saga | S1~S3 통합 테스트, compose로 전체 실행 | — |
| W2 | M2 장애 격리·관측 | 서비스 간·PG 호출 서킷 브레이커, 결과 재조회, Toxiproxy, OpenTelemetry·Jaeger·Prometheus·Grafana | S4~S6 전후 숫자 | 1편: PG가 느려지면 왜 우리 서비스가 다 느려질까 |
| W3 | M3 노출·과금·정산 | delivery(대량 수집·집계·예산 차감), settlement(원장·정산서), Inbox | S7~S9, k6 처리량 숫자 | 2편: 노출 이벤트 초당 N건에서 예산을 넘기지 않고 과금하기 |
| W4 | M4 서버 주도 화면 | experience(SDUI BFF), web 렌더러, 컴포넌트 버전·대체 표시, 화면 설정 | S10~S12, 화면 녹화 | 3편: 앱 배포 없이 화면 바꾸기, SDUI를 직접 만들어 보며 정한 경계 |
| W5 | M5 AI 에이전트 | agent(MCP), 위임 한도, 승인 흐름(SDUI 승인 화면), 감사 로그, 인젝션 평가 | S13~S17, 평가 결과 | 4편: 운영 요청을 AI 에이전트에게, 돈은 코드가 지키게 |
| W6 | 검증·정리 | 검증 문서, README, 아키텍처 그림, 포트폴리오, 이력서 갱신 | README만 보고 5분 안에 실행 | — |

## 4.4 위험과 대응

| 위험 | 대응 |
| --- | --- |
| 서비스가 많아 로컬 메모리가 부족 | JVM 메모리 상한을 서비스마다 둔다. PC 32GB, Docker 16GB 확인 |
| MSA가 목적이 되어 복잡도만 커짐 | 서비스 경계마다 "왜 나눴는가"를 ADR에 남긴다. 나눌 이유가 약하면 합친다 |
| 가설이 틀림 | 틀린 결과도 검증 문서에 남기고, 무엇을 바꿨는지 적는다 |
| 일정 지연 | 블로그와 마일스톤을 묶어, 늦어지면 M4·M5 범위를 줄이고 M1~M3를 먼저 끝낸다 |

# ADR-0002. 코레오그래피 Saga + Transactional Outbox(폴링) + Inbox

- 날짜: 2026-11-21 · 상태: 채택

## 상황
주문(campaign)과 결제(payment)는 서로 다른 DB에 있다. "주문 생성 후 결제", "결제 실패 시 주문 취소"를 하나의 DB 트랜잭션으로 묶을 수 없다. DB에 쓰고 Kafka 발행에 실패하거나, 그 반대가 되면 돈과 상태가 어긋난다.

## 선택지
| 축 | 선택지 |
| --- | --- |
| Saga 방식 | A. 코레오그래피(각 서비스가 이벤트에 반응) / B. 오케스트레이션(중앙 조정자) |
| 발행 보장 | A. Outbox + 폴링 릴레이 / B. Outbox + CDC(Debezium) / C. DB 쓰기 후 바로 발행 |
| 소비 멱등 | A. Inbox 테이블(이벤트 ID) / B. 업무 키 유니크 제약만 |

## 결정
- **코레오그래피.** 참여 서비스가 2~3개이고 흐름이 짧다. 조정자 서비스를 하나 더 두는 비용이 크다.
- **Outbox + 폴링 릴레이.** 상태 변경과 같은 트랜잭션에서 `outbox_events`에 쓰고, 릴레이가 `FOR UPDATE SKIP LOCKED`로 가져가 발행한 뒤 표시한다. 발행 지연은 폴링 주기(기본 200ms)만큼 생긴다.
- **Inbox + 업무 키 유니크 둘 다.** Inbox로 같은 이벤트를 건너뛰고, 결제의 `order_id` 유니크처럼 업무 키로 한 번 더 막는다.

## 이유
- 폴링은 인프라가 Postgres·Kafka뿐이라 로컬에서 재현이 쉽다. 이 규모에서는 지연·부하가 문제가 되지 않는다.
- 릴레이는 "최소 한 번" 발행이다. 중복은 소비 쪽 Inbox가 흡수한다. 정확히 한 번은 발행이 아니라 "효과"로 보장한다.
- (2026-11-21 M3 수정) 릴레이는 가져온 행(최대 100건)을 한꺼번에 보내고 모두 확인된 뒤 표시한다. 처음에는 같은 키의 순서를 지키려고 한 건씩 보내고 기다렸는데, 초당 약 160건이 한계라 S7에서 과금 이벤트 3만 건을 발행하는 데 196초가 걸렸다. 멱등 프로듀서(기본값, acks=all)는 같은 파티션 안의 순서를 지키므로 한꺼번에 보내도 키별 순서는 그대로다. 일부가 실패하면 묶음 전체를 다음 회차에 다시 보낸다(중복은 Inbox가 흡수).

## 포기한 것
- CDC(Debezium): 발행 지연이 짧고 DB 부하가 적지만 Kafka Connect 운영이 늘어난다. 처리량 실험(M3)에서 폴링이 병목이면 다시 검토한다.
- 오케스트레이션: 흐름이 한눈에 보이지만, 단계가 늘기 전에는 과하다. 환불 흐름이 복잡해지면 다시 검토한다.

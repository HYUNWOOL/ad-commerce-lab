# ADR-0006. PG가 받지 않은 결제는 실패 대신 보류한다

- 날짜: 2026-11-21 · 상태: 채택(S4 실험 결과로 ADR-0003의 "서킷이 열리면 바로 실패" 동작을 바꿈)

## 상황
S4 실험(PG 지연 2.5초 + 503 50%, 60초)에서 서킷을 켜자 장애 중 PG가 받은 승인 요청은 79건 → 21건으로 줄고 결제 확정도 0.3초(p50)로 빨라졌다. 대신 300건 중 292건이 PG_UNAVAILABLE로 취소됐다. 1분짜리 PG 장애가 주문 292건 취소가 된 것이다. 서킷은 PG와 우리 쪽 자원을 지켰지만, "열렸을 때 무엇을 할지"를 실패로 정해 둔 탓에 매출을 잃었다.

## 결정
1. PG가 받지 않았다고 확신할 수 있는 결과(503, 연결 실패, 서킷 열림)는 결제를 REQUESTED로 두고 사유(PG_UNAVAILABLE)만 남긴다. 주문은 PAYMENT_PENDING("결제 확인 중")에 머문다.
2. 재조회(ADR-0004)가 15초 뒤 집어서 PG에 조회하고, 없으면 같은 멱등키로 다시 보낸다. 서킷이 아직 열려 있으면 PG를 부르지 않고 다음 회차로 넘긴다. 그래서 PG를 두드리지 않는다.
3. 결제를 만든 지 10분이 지났고 PG에도 없으면 다시 보내지 않고 PG_UNAVAILABLE로 실패시킨다(주문 취소). PG가 한 번도 처리하지 않은 결제라 돈이 어긋나지 않는다.
4. 다시 보낸 승인이 타임아웃되면 UNKNOWN으로 옮긴다. 이때부터는 PG가 처리했을 수 있으므로 기한이 지나도 PG에 없다는 확인 없이는 실패로 만들지 않는다.
5. 비교 실험을 위해 `payment.pg-unavailable=fail`(바로 실패)을 남긴다. 기본값은 `defer`.

## 포기한 것
- 바로 실패: 파트너가 즉시 결과를 알고 다시 주문할 수 있지만, 짧은 장애에도 주문을 잃는다. 광고 구매는 몇 분 늦어도 되는 결제라 기다리는 쪽을 택했다.
- Kafka 재시도 토픽·DLQ로 보류: 메시지를 다시 돌리는 구조가 하나 더 생긴다. 이미 있는 재조회 스케줄러와 DB 상태로 같은 일을 한다.
- 컨슈머 일시 정지(서킷이 열리면 리스너를 멈춤): 밀린 주문이 Kafka에 쌓여 "결제 확인 중"인지조차 알 수 없다. DB에 보류 상태로 남기면 조회 API로 보인다.

## 결과
같은 S4에서 보류로 바꾸자 장애 중 PG 요청 21건(바로 실패와 같음), 컨슈머 지연 최대 33건, 주문 300건 모두 PAID. 대신 결제 확정 p50이 39.3초로, 보호 없음(30.6초)보다 길었다. 비교 전체는 [m2-resilience.md](../../04-verification/m2-resilience.md).

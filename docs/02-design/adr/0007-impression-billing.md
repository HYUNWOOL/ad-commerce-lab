# ADR-0007. 노출 수집·과금: Kafka 배치를 창으로, 중복은 DB 유니크로

- 날짜: 2026-11-21 · 상태: 채택(S7 실측으로 Redis 보류 확정, 배치 채우기 추가)

## 실측 뒤 바꾼 것 (S7, [m3-billing.md](../../04-verification/m3-billing.md))
- **Redis는 넣지 않는다.** DB만으로 초당 1만 건(목표의 2배)에서도 과금 지연 p95 0.2초, 부하가 끝나고 2초 안에 다 따라잡았다.
- **배치를 채운다**(`fetch-min-size 128KB`, `fetch-max-wait 500ms`). 첫 실행에서는 컨슈머가 들어오는 대로 몇십 건씩 가져가 과금 이벤트가 노출 9.4건당 1건(3만 건)으로 불어났고, 그 이벤트를 받아 적는 원장이 부하가 끝난 뒤 148초나 늦었다. 배치를 채우고 Outbox 릴레이를 한꺼번에 보내도록 바꾸자(ADR-0002, 두 가지를 함께 바꿔서 각각의 몫은 나눠 재지 않았다) 노출 86건당 1건(3,478건), 원장 지연 5초. 대가로 과금 지연 p95가 54ms → 327ms로 늘었다(목표 2초 안).
- **정적 멤버십**(`group.instance.id = delivery-${HOSTNAME}`). S9에서 delivery를 강제 종료하고 다시 띄우자 앱은 4초 만에 떴는데, 컨슈머 그룹이 죽은 멤버의 세션 타임아웃(기본 45초)을 기다리느라 파티션을 39초 뒤에야 다시 받았다. 그동안 과금이 멈춰 과금 지연 p50이 21초였다. 정적 멤버십을 켜자 같은 인스턴스가 뜨자마자(0.02초) 자기 파티션을 받았고 p50 0.13초. 과금 정확도는 두 경우 모두 차이 0이었다. 인스턴스가 아예 돌아오지 않으면 여전히 세션 타임아웃 뒤에 다른 인스턴스로 넘어간다.

## 상황
노출 이벤트는 초당 수천 건 들어온다(S7). 같은 이벤트가 두 번 오거나 처리 도중 죽어도 한 번만 과금해야 하고(S9), 예산을 넘겨 과금하면 안 된다(S8). 설계 초안(02-domain-model 2.5)은 "캠페인별 1초 창 + Redis·DB 이중 중복 확인"이었다.

## 결정
1. **수집**: delivery `POST /impressions`(내부망, 광고 서버가 부른다. gateway를 거치지 않는다). 한 요청에 최대 500건. 형식만 검사하고 Kafka `delivery.impression`(키 = campaignId)에 넣은 뒤 브로커 확인(acks=all)을 받으면 202. DB는 건드리지 않는다.
2. **창 = Kafka 배치**: 배치 리스너가 한 번에 받은 메시지(최대 500건)를 트랜잭션 하나로 처리한다. 시간 창을 위한 버퍼·타이머가 필요 없고, 캠페인당 UPDATE가 배치마다 한 번이다.
   1. `impression_events`(PK event_id)에 `INSERT … ON CONFLICT DO NOTHING RETURNING`으로 처음 본 이벤트만 남긴다.
   2. 캠페인별 개수 × 단가를 남은 예산 안에서만 한 문장으로 차감한다: `spent + LEAST(개수, (budget − spent) / cpv) × cpv`.
   3. 차감 기록(`charges`) + Outbox `CampaignCharged`. 남은 예산이 단가보다 작아지면 EXHAUSTED + `BudgetExhausted`.
   4. Kafka 오프셋은 DB 커밋 뒤에 커밋된다. 커밋 전에 죽으면 배치를 다시 받고, 이미 넣은 event_id는 1번에서 걸러진다(S9).
3. **예산의 원본은 delivery**(`campaign_budgets`). `CampaignActivated`로 만들고, campaign 서비스는 `CampaignCharged`의 누적 사용액을 화면용으로 복제한다.
4. **모르는·멈춘 캠페인의 노출**은 기록만 하고 과금하지 않는다. 틀린다면 덜 받는 쪽으로 틀린다.
5. **실패한 배치는 버리지 않는다.** 공통 오류 처리기(1초부터 최대 10초 간격, 무한 재시도)로 다시 처리한다. 형식이 깨진 메시지는 그 건만 건너뛰고 로그를 남긴다. Spring Kafka 기본 처리기는 10번 실패하면 메시지를 버리고 넘어가는데, 결제·과금 이벤트에서는 돈이 사라지는 것과 같다(M1·M2의 리스너에도 함께 적용).

## 포기한 것
- **Redis 중복 확인·예산 카운터**: 새 이벤트는 어차피 DB에 넣어야 최종 중복 확인이 되므로 Redis는 중복분의 DB 쓰기만 줄인다. 예산을 Redis에서 깎으면 돈의 원본이 둘이 되고, Redis 장애 때 어느 쪽이 맞는지 따로 맞춰야 한다. S7에서 DB만으로 목표 처리량을 넘지 못하면 다시 본다.
- **노출마다 UPDATE**: 인기 캠페인 한 행에 잠금이 몰린다.
- **Kafka Streams**: 창 집계는 깔끔하지만 상태 저장소·재처리 운영을 새로 배워야 하고, 돈의 원본이 DB 밖에 생긴다.
- **원시 노출을 영원히 보관**: 지금은 `impression_events`가 계속 자란다. 운영이라면 날짜 파티션을 두고 중복 확인 기간(예: 7일)이 지난 파티션을 지운다.

# ADR-0008. 정산 원장: 복식부기, 균형은 DB가 강제한다

- 날짜: 2026-11-21 · 상태: 채택

## 상황
결제·과금이 각 서비스에 흩어져 있으면 "이 파트너에게 받은 돈과 쓴 돈, 남은 돈"을 한 곳에서 말할 수 없다(FR-401~403, S9). 정산 숫자는 다른 서비스가 틀려도 스스로 맞는지 검산할 수 있어야 한다.

## 결정
1. **이벤트 하나 = 분개 하나.** `journal_entries`(source_event_id UNIQUE)와 `journal_lines`(계정, 파트너, 차변, 대변)로 나눈다. 한 줄은 차변·대변 중 한쪽만 양수다.
2. **균형은 DB가 강제한다.** 커밋 시점에 도는 제약 트리거(`DEFERRABLE INITIALLY DEFERRED`)가 분개마다 차변 합 = 대변 합인지 확인한다. 코드가 한쪽 줄만 쓰는 실수를 해도 커밋되지 않는다.
3. **계정**

   | 사건 | 차변 | 대변 |
   | --- | --- | --- |
   | 결제 승인(PaymentApproved) | PG_RECEIVABLE(PG 미수금) | PARTNER_PREPAID(파트너 선수금) |
   | 노출 과금(CampaignCharged) | PARTNER_PREPAID | AD_REVENUE(광고 매출) |

   환불은 결제 서비스에 아직 없어 M3 범위 밖이다(차변 PARTNER_PREPAID / 대변 PG_RECEIVABLE로 넣을 자리만 둔다).
4. **정산서**: 파트너 + 월(Asia/Seoul 기준). 결제액 = 그달 선수금 대변(결제), 사용액 = 그달 선수금 차변(과금), 잔액 = 월말까지의 선수금 대변 누계 − 차변 누계. 모두 원장 합계 쿼리로 구한다.
5. **멱등**: Inbox(`processed_events`) + `source_event_id` UNIQUE 이중 확인.
6. 파트너는 자기 정산서만 본다. gateway가 넣어 주는 `X-Partner-Id`로만 거르고, 쿼리 파라미터의 파트너 ID는 받지 않는다.

## 포기한 것
- **잔액 테이블을 분개마다 갱신**: 조회는 빠르지만 파트너 한 행에 잠금이 몰리고, 원장과 잔액이 어긋날 수 있는 곳이 하나 더 생긴다. 지금 양에서는 합계 쿼리로 충분하다.
- **애플리케이션 검사만**: 테스트로는 막을 수 있지만, 나중에 다른 코드 경로(수기 보정, 배치)가 생기면 다시 막아야 한다. 원장 테이블 자체가 불변식을 갖게 했다.

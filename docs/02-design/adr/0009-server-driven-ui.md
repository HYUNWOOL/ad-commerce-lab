# ADR-0009. 서버 주도 화면(SDUI): 화면은 설정, 데이터는 영역별, 버전은 서버가 맞춘다

- 날짜: 2026-11-22 · 상태: 채택

## 상황
P2: 문구 하나, 섹션 순서 하나를 바꾸는 데 앱 배포와 스토어 심사를 기다렸고, 업데이트하지 않은 사용자에게는 끝까지 반영되지 않았다. 원격 설정으로는 값만 바꿀 수 있고 화면 구조는 못 바꿨다(FR-501~505, S10~S12).

## 결정
1. **화면 = 섹션 목록.** 응답은 `{screenId, revision, sections: [{id, type, version, props}]}`. 클라이언트는 섹션을 순서대로 그리기만 한다. 섹션 순서·문구·노출 여부는 서버 설정이다.
2. **설정은 리비전으로 쌓는다.** `screen_revisions(screen_id, revision, layout)`에 새 리비전을 추가하고 최신을 내려준다. 운영자는 `PUT /api/admin/screens/{id}`에 `baseRevision`을 함께 보낸다. 그사이 다른 사람이 바꿨으면 409(덮어쓰기 방지). 저장 전에 컴포넌트 종류·버전·데이터 출처·필수 문구를 검사해, 설정 실수로 화면이 깨지지 않게 한다(400). 되돌리기는 옛 리비전의 layout을 다시 저장한다.
3. **데이터는 섹션마다 출처(source)를 갖는다.** 예: 성과 목록 → delivery, 정산 요약 → settlement, 상품 목록 → catalog. 한 화면이 쓰는 출처를 병렬로 부르고(가상 스레드), 출처마다 타임아웃 1초 + 서킷 브레이커를 둔다(ADR-0003). 실패한 출처를 쓰는 섹션만 `Fallback`으로 바꾸고 나머지는 그린다(S12). 화면 전체를 실패시키지 않는다.
4. **버전은 서버가 맞춘다.** 클라이언트는 `X-Client-Components: Banner@1,CampaignPerformanceList@2,...`로 아는 컴포넌트와 최고 버전을 보낸다. 서버는 섹션마다 `min(설정 버전, 클라이언트 버전)`으로 내려보내고, 옛 버전으로 낮출 때 필드를 덜어 낸다(예: 성과 목록 v2 → v1은 노출 수·진행률을 뺀다). 클라이언트가 모르는 종류면 그 섹션만 `Fallback`("앱을 업데이트하면 볼 수 있어요")으로 바꾼다(S11).
5. **클라이언트도 한 번 더 막는다.** 렌더러는 모르는 종류를 받으면 그 섹션만 대체 표시하고, 섹션 하나가 그리다 터져도 섹션 단위 오류 경계에서 멈춘다. 서버 설정이 틀려도 화면 전체가 하얗게 되지 않는다.
6. **행동도 데이터다.** 버튼은 `{type: "navigate", screen}` 또는 `{type: "submit", ...}`을 받는다. 구매 폼은 기존 주문 API(멱등키)를 그대로 쓴다. 돈과 상태의 규칙은 여전히 업무 서비스가 가진다.
7. **권한**: 화면 조회는 파트너 키, 설정 변경은 운영자 키로만 한다. gateway가 `/api/admin` 아래에는 운영자 키만 받고 `X-Operator-Id`를 붙인다.

## 포기한 것
- **화면 전체를 서버가 HTML로 그리기(서버 렌더링)**: 웹에는 맞지만 네이티브 앱은 못 쓴다. P2의 핵심은 네이티브 앱 배포 대기다.
- **범용 레이아웃 언어(행·열·여백까지 서버가 지정)**: 무엇이든 바꿀 수 있지만 디자인 시스템이 서버로 새고, 클라이언트가 모든 조합을 감당해야 한다. 업무 의미가 있는 컴포넌트(성과 목록, 정산 요약) 단위로 자른다.
- **출처별 캐시(마지막 성공 값)**: 장애 때 옛 값을 보여 줄 수 있지만 돈이 걸린 숫자(남은 예산)를 오래된 값으로 보여 주게 된다. 지금은 대체 표시만 한다.
- **설정 미리보기·예약 반영**: 운영 기능으로 필요하지만 M4 범위 밖이다.

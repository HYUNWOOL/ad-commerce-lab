# M2 장애 격리 실험 결과 (S4~S6)

- 날짜: 2026-11-21 · 환경: [검증 README](README.md)의 로컬 compose
- 다시 돌리기: `bash scripts/experiments/m2.sh s4 off|fail|on`, `s5`, `s6 off|on`
- 가설(기획 01-problem): 외부 PG 장애가 우리 서비스로 번지는 것은 동기 호출이 자원을 붙잡기 때문이고, 비동기 경계 + 타임아웃 + 서킷 브레이커 + 결과 재조회로 막을 수 있다.

## S4. PG 지연 2.5초 + 503 50% (60초)

부하: 주문 5건/초 + 캠페인 조회 20건/초, 60초(k6). 장애는 부하가 끝날 때 함께 풀린다. 매 실행마다 campaign·payment를 새로 띄워 서킷 상태를 비운다.

| | off: 보호 없음 | fail: 서킷 + 바로 실패 | on: 서킷 + 보류(ADR-0006) |
| --- | --- | --- | --- |
| 주문 API p95 (k6) | 31ms | 34ms | 40ms |
| 조회 API p95 (k6) | 16ms | 26ms | 20ms |
| 주문·조회 API 오류율 | 0% | 0% | 0% |
| **장애 중**(60초) PG가 받은 승인 요청 | 79건 | 21건 | 21건 |
| 복구 뒤 PG가 받은 승인 요청 | 267건 | 0건 | 288건 |
| 결제 확정까지 p50 / p95 / 최대 | 30.6 / 59.0 / 68.0초 | 0.3 / 6.7 / 10.3초(대부분 취소) | 39.3 / 65.9 / 69.2초 |
| 결과 | PAID 301 | PAID 8, CANCELLED 292 | PAID 300 |
| 결제 컨슈머 최대 지연(브로커 기준) | 253건 | 41건 | 33건 |
| pg 서킷이 막은 시간(열림·반열림, 5초 표본) | 0초 | 약 50초 | 약 55초 |

읽는 법
- 세 설정 모두 파트너 API(주문·조회)는 수십 ms 안이었고 오류도 없었다. 결제가 Kafka 뒤에 있어 PG 지연이 API로 오지 않는다. 가설의 "번짐"은 서킷 브레이커보다 비동기 경계가 먼저 막았다.
- 보호 없음은 아픈 PG에 79건을 보냈다. 컨슈머가 3개뿐이라 두드리는 양이 이 정도로 묶였다(동기 호출에 요청 스레드 수백 개였다면 훨씬 많았을 것이다). 대신 처리량이 초당 1.2건으로 떨어져, 들어오는 초당 5건과의 차이만큼 Kafka에 쌓였다(60초에 253건). 장애가 길어지면 이 지연은 초당 약 3.8건씩 계속 늘어난다(측정은 60초까지만 함).
- 서킷 + 바로 실패는 아픈 PG에 21건만 보냈지만 1분 장애로 주문 97%를 잃었다. 이 결과로 ADR-0006(보류)을 정했다.
- 서킷 + 보류는 아픈 PG에 21건만 보내고, 컨슈머 지연도 33건에서 멈췄으며, 주문을 하나도 잃지 않았다. 대가는 확정 시간이다. 보류한 결제는 장애가 끝난 뒤 재조회 회차(15초 대기, 5초 주기)와 서킷이 반열림으로 바뀌는 시간을 기다려, p50이 보호 없음보다 9초 길었다.
- 세 설정의 전체 PG 요청 수(346 / 21 / 309)는 비교 지표로 쓰지 않는다. 복구 뒤에 처리된 요청까지 섞여 "아픈 PG를 얼마나 두드렸나"를 보여 주지 못한다. 장애 중 숫자는 실행마다 주문이 들어온 구간의 mock-pg 요청 카운터(Prometheus) 차이로 구했다.

참고: off에서 PG 요청이 주문보다 많은 것(346 > 301)은 503을 받은 결제를 보류했다가 같은 멱등키로 다시 보냈기 때문이다(ADR-0006 이후 코드). 같은 off를 바로 실패 코드로 돌렸을 때는 PAID 269, CANCELLED 31, PG 300건이었다.

## S5. 결과를 모르는 결제 → 재조회로 확정

| 실행 | 주입 | 결과 |
| --- | --- | --- |
| A-1 (서킷 하나) | PG가 3.5초 뒤 처리, 우리 타임아웃 3초. 주문 8건 | 8건 모두 UNKNOWN → APPROVED. 확정 p50 22.8초. 재조회 1~3회(승인 타임아웃이 하나뿐인 서킷을 열어 조회까지 막음) |
| A-2 (승인·조회 서킷 분리) | 같음 | 8건 모두 UNKNOWN → APPROVED. 확정 p50 13.3초 / p95 17.9초. **모두 재조회 1회**. PG 승인 요청 8건(조회로 끝나 재승인 없음) |
| B | PG로 가는 데이터를 20초 동안 버림(Toxiproxy timeout). 주문 4건 | 20초 뒤 4건 UNKNOWN. 복구 뒤 첫 재조회에서 "PG에 없음" → 같은 멱등키로 재승인 → 4건 PAID. PG에 기록된 결제 4/4, PG 승인 요청 4건 |

- 사람이 확인한 건은 0건. 중복 승인 0건(결제 ID = PG 멱등키, 결제는 주문당 하나).
- A-1 → A-2 사이에 ADR-0004 5번(승인 `pg` / 조회 `pg-query` 서킷 분리)을 넣었다.
- B를 A 바로 뒤에 돌리면 A의 승인 타임아웃이 서킷 창에 남아 B의 새 결제 2건이 바로 실패했다(서킷이 의도대로 동작한 것). 실험끼리 섞이지 않게 B 앞에서 payment를 새로 띄운다.

## S6. 내부 동기 호출 대상(catalog) 지연 3초

부하: 주문 20건/초 + 조회 20건/초, 60초. campaign 요청 스레드를 40개로 줄여 둔다(두 실행 모두). 주문은 campaign → catalog를 동기로 부르고, 조회(`GET /campaigns`)는 catalog를 부르지 않는다.

| | off: 타임아웃 30초, 서킷 없음 | on: 타임아웃 1초 + 서킷 |
| --- | --- | --- |
| **조회 API**(`GET /campaigns`, catalog와 무관) p50 / p95 | **7,770ms / 10,001ms** | 21ms / 27ms |
| 조회 API 오류율(k6 타임아웃 10초 포함) | **36.9%** | 0% |
| 주문 API p50 / p95 | 9,999ms / 10,001ms | 3ms / 5ms |
| 주문 API 오류율 | 56.6%(타임아웃) | 100%(즉시 503 + Retry-After 10) |
| k6가 보내지 못한 요청(가상 사용자 400명 모두 대기 중) | 281건 | 0건 |
| campaign 요청 스레드 최대 사용 | **40 / 40** | 4 / 40 |
| catalog 서킷이 막은 시간 | 0초 | 약 60초(장애 내내) |

읽는 법
- 보호가 없으면 catalog를 기다리는 주문 요청이 campaign의 요청 스레드 40개를 모두 붙잡았다. catalog를 부르지도 않는 조회 API가 스레드를 얻지 못해 p95 10초, 오류 37%가 됐다. 이것이 P1에서 말한 "번짐"이다.
- 타임아웃 1초 + 서킷이면 처음 몇 건만 1초를 기다리고(주문 최대 1,158ms) 곧 서킷이 열려 주문은 즉시 503을 받는다. 스레드는 4개만 쓰였고 조회 API는 장애가 없을 때와 같았다.
- 대가: catalog가 아픈 동안 주문은 하나도 받지 못한다. 보호 없음에서는 주문의 43%가 결국(3초 넘게 기다려) 들어갔다. ADR-0003에서 "오래된 가격 캐시로 주문을 받지 않는다"고 정했기 때문이다. 주문 화면(experience, M4)은 캐시나 대체 표시로 버티게 한다.
- 실험 중 스크립트를 고쳐 첫 실행의 마지막 정리 줄이 실행되지 않았다(bash가 실행 중인 파일을 이어 읽음). 결과 숫자에는 영향이 없고, 두 번째 실행이 처음부터 다시 정리했다.

## 관측에서 확인한 것
- 주문 하나가 서비스 5개와 Kafka 두 번을 지나 한 트레이스로 보인다(`python scripts/trace.py`, [flow-m2.md](../03-development/flow-m2.md)). Outbox 행에 `traceparent`를 저장해 릴레이 구간도 이어진다.
- Kafka 클라이언트 `records-lag` 지표는 S4 off에서 253건이 밀리는 동안 0이었다. 가져온 뒤 처리 못 한 메시지를 세지 않는다. 컨슈머 지연은 브로커 기준으로 본다(ADR-0005).

## 가설 판정

| 가설 | 판정 | 근거 |
| --- | --- | --- |
| 외부 장애의 번짐은 동기 호출이 자원(스레드)을 붙잡아서 생긴다 | 맞음 | S6 off: 스레드 40/40, 무관한 조회 API p95 10초·오류 37% |
| 타임아웃 + 서킷이 번짐을 막는다 | 맞음 | S6 on: 스레드 4/40, 조회 p95 27ms |
| 비동기 경계(Kafka)가 외부 PG 장애를 API에서 떼어 낸다 | 맞음 | S4 세 설정 모두 주문·조회 API p95 40ms 이하, 오류 0 |
| 서킷 브레이커가 장애 중 결제를 지킨다 | **절반만 맞음** | PG 부하는 79 → 21건으로 줄었지만, 열렸을 때 바로 실패시키면 주문 97%를 잃었다. 보류(ADR-0006)를 더해서야 PG 부하 21건과 주문 손실 0을 함께 얻었다 |
| 결과를 모르는 결제는 사람 없이 확정할 수 있다 | 맞음 | S5: 12건 모두 재조회로 확정, 중복 승인 0. 단, 승인·조회 서킷을 나눠야 했다 |

## 측정하지 못한 것
- 장애가 10분을 넘겨 보류 기한에 걸리는 경우. 보류된 결제가 한꺼번에 취소되며, 그때 파트너에게 보여 줄 내용은 정하지 않았다.
- 재조회로 확정된 결제는 원래 트레이스와 이어지지 않는다(재조회 스레드에는 원래 요청의 문맥이 없고, 결제 행에 traceparent를 저장하지 않았다).
- 노트북 한 대의 Docker에서 잰 숫자라 절대값보다 설정 사이의 차이만 의미가 있다.

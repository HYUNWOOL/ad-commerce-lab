# M3 노출 과금 실험 결과 (S7~S9)

- 날짜: 2026-11-21 · 환경: [검증 README](README.md)의 로컬 compose(컨테이너 14개)
- 다시 돌리기: `bash scripts/experiments/m3.sh s7 [초당 요청 수]`, `s8`, `s9`
- 공통: k6가 광고 서버처럼 노출을 100건씩 묶어 delivery 수집 API로 60초 동안 보낸다. 실험마다 새 캠페인 10개(예산 300만 원, 단가 50원)를 주문·결제 흐름으로 만든다. 202를 못 받은 요청은 같은 본문으로 다시 보낸다.
- 검산: 캠페인마다 `과금한 노출(사용액 ÷ 단가) = min(처음 본 노출, 예산 ÷ 단가)`, `charges 합 = 사용액`, `사용액 ≤ 예산`, 원장 선수금 차변 합 = delivery 사용액 합, 원장 차변 합 = 대변 합.

## S7. 처리량

| | 첫 실행(초당 5천) | 배치 채우기 + 릴레이 일괄 발행(초당 5천) | 같은 코드, 초당 1만 |
| --- | --- | --- | --- |
| 보낸 노출 / 과금한 노출 | 300,100 / 300,100 | 300,100 / 300,100 | 600,100 / 598,934(일부 캠페인 예산 소진, 기대값과 차이 0) |
| 수집 API p50 / p95 / p99 | 8 / 12 / 19ms | 9 / 11 / 13ms | 9 / 12 / 175ms |
| 과금 지연 p50 / p95 / p99 | 9 / 54 / 104ms | 91 / 327 / 393ms | 61 / 201 / 1,619ms |
| 부하가 끝난 뒤 과금 컨슈머 따라잡기 | 2초 | 2초 | 2초 |
| 과금 이벤트(CampaignCharged) | **31,804건**(노출 9.4건당 1건) | 3,478건(86.3건당 1건) | 5,874건(102건당 1건) |
| Outbox 발행 | 196초 | 60초(부하와 함께 끝남) | 60초 |
| 부하가 끝난 뒤 원장이 따라잡기 | **148초** | 5초 | 5초 |

- 과금 자체(노출 INSERT + 예산 UPDATE)는 첫 실행부터 목표를 넘었다. Redis 없이 DB만으로 충분했다(ADR-0007).
- 문제는 과금 뒤였다. 컨슈머가 들어오는 대로 몇십 건씩 가져가 배치가 작았고, 배치·캠페인마다 과금 이벤트가 하나씩 나가 3만 건이 됐다. Outbox 릴레이는 순서를 지키려고 한 건씩 보내고 기다려 초당 약 160건이 한계였다. 그 결과 원장(정산)은 부하가 끝난 뒤에도 2분 넘게 늦었다.
- 두 가지를 함께 바꿨다: 컨슈머가 최대 500ms 기다려 배치를 채우게 했고(`fetch-min-size 128KB`, `fetch-max-wait 500ms`), 릴레이는 묶음을 한꺼번에 보내고 모두 확인하게 했다(ADR-0002). 각각의 몫은 나눠 재지 않았다.
- 대가: 배치를 채우려고 기다리는 만큼 과금 지연 p95가 54ms → 327ms로 늘었다. 예산 소진 판단이 그만큼 늦어지지만, 예산 초과는 SQL의 `LEAST`가 막으므로 늦어도 넘겨 과금하지는 않는다.

## S9. 재전송 20% + 처리 도중 강제 종료

노출의 20%를 이미 보낸 eventId로 다시 보내고, 20초에 delivery를 SIGKILL로 죽인 뒤 바로 다시 띄웠다(수집 API와 과금 컨슈머가 함께 죽는다). k6는 202를 못 받은 요청을 같은 본문으로 다시 보낸다.

| | 정적 멤버십 없음 | 정적 멤버십(`group.instance.id`) |
| --- | --- | --- |
| 처음 노출 / 재전송 | 235,440 / 53,660 | 237,103 / 54,097 |
| 실패해서 다시 보낸 요청 | 714 | 559 |
| 과금한 노출 | 235,440(차이 0) | 237,103(차이 0) |
| 앱이 다시 뜬 뒤 파티션을 받기까지 | **39초**(죽은 멤버의 세션 타임아웃 대기) | **0.02초** |
| 과금 지연 p50 / p95 / p99 | 21초 / 30초 이상 / 30초 이상 | 0.13 / 3.2 / 5.5초 |
| 원장 | 일치 | 일치 |

- 과금은 두 경우 모두 정확했다. 커밋 전에 죽은 배치는 오프셋도 커밋되지 않아 다시 받았고, 이미 커밋된 노출과 재전송은 `impression_events` PK에서 걸러졌다.
- 정확하다고 끝이 아니었다. 정적 멤버십이 없으면 죽은 멤버가 세션 타임아웃(45초)까지 파티션을 쥐고 있어, 앱이 4초 만에 다시 떠도 과금이 40초 넘게 멈췄다.
- "30초 이상": 과금 지연 타이머의 히스토그램 상한이 30초라 그 위는 구분하지 못한다.

## 실험하면서 고친 실험 도구
- `wait`가 끝나지 않는 지연 감시 작업까지 기다려 스크립트가 멈췄다 → 강제 종료 작업만 기다린다.
- 3초마다 `kafka-consumer-groups.sh`를 불러 Kafka 컨테이너 CPU가 300%를 넘었다(부를 때마다 JVM이 뜬다) → 실험 끝에 지연이 0인지만 5초 간격으로 확인.
- `docker kill`은 "직접 멈춤"으로 쳐서 재시작 정책이 다시 띄우지 않았다 → 스크립트가 바로 `docker start`.
- 멈춘 첫 실행의 프로세스가 남아 다음 실험 중에도 Kafka를 두드렸다 → 찾아서 종료한 뒤 S8·S9를 다시 돌렸다.

## 측정하지 못한 것
- 인스턴스가 아예 돌아오지 않는 경우(다른 인스턴스로 넘어가기). 지금은 delivery가 하나뿐이다.
- 초당 1만 건 이상의 한계, 몇 시간짜리 부하에서 `impression_events`가 커질 때의 INSERT 속도(파티션 정리 없음).
- M3 이전에 쌓인 `PaymentApproved`에는 `partnerId`가 없어 정산 원장이 건너뛴다(로그만 남김). 그래서 원장 검산은 delivery 사용액(과금)과 비교했다.

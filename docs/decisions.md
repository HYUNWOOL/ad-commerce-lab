# 결정 기록

형식: 상황 · 선택지 · 결정 · 이유 · 포기한 것. 면접에서 그대로 설명할 수 있게 쓴다. 설계 단계의 세부 결정은 docs/02-design/adr에 따로 남기고 여기서는 목록만 잇는다.

## D1. 주제: 현업 불편 세 가지를 가상의 광고 커머스 플랫폼에서 검증 (2026-11-21)
- 상황: 실무에서 겪은 불편은 외부 PG 장애 전파, 앱 배포에 묶인 화면 변경, 개발자에게 오는 운영 요청이다. 이력서의 다음 목표는 "AI가 틀려도 돈은 틀리지 않는 시스템"이다.
- 선택지: A. 일반 대용량 커머스(선착순·재고) / B. B2C 쇼핑 에이전트 결제 / C. 파트너 광고 구매·과금·정산 플랫폼 + 에이전트 구매·운영 에이전트.
- 결정: C. 가상의 동네 매장 예약 플랫폼 "Nearby"를 무대로 한다.
- 이유: 실제로 겪은 불편에서 출발해야 면접에서 "왜 만들었나"에 답할 수 있다. 광고 구매·노출·과금·정산은 직접 해 본 도메인이라 깊이가 생기고, 에이전트 결제 트렌드(ACP·AP2)와 운영 에이전트를 함께 넣을 수 있다.
- 포기한 것: 선착순·재고 같은 트래픽 폭주 서사. 대신 노출 이벤트 파이프라인으로 대용량 처리를 보여 준다. 실제 회사 이름·데이터·수치는 쓰지 않는다.

## D2. 언어: 업무 서비스는 Kotlin + Spring Boot, 에이전트는 Python (2026-11-21)
- 상황: 이력서의 주력은 Python이고 Java/Spring은 실무 경험 수준. 국내 커머스·핀테크 공고는 Java·Kotlin·Spring·Kafka가 중심이다.
- 선택지: A. 전부 Python / B. 전부 Kotlin / C. 업무 서비스는 Kotlin, 에이전트는 Python.
- 결정: C.
- 이유: JVM 주력 역량의 증거가 이직 시장에서 가장 큰 공백이다. LLM 생태계(MCP SDK, Anthropic SDK)는 Python이 가장 성숙하고 이미 다뤄 봤다. 실제 회사도 이렇게 나뉘는 경우가 많다.
- 포기한 것: 언어 하나로 통일하는 단순함. 멱등키 같은 공통 규칙을 Python 쪽에서 한 번 더 구현해야 한다.

## D3. 배포: 로컬 Docker Compose + 녹화·결과 숫자 (2026-11-21)
- 상황: 서비스 8~9개와 Kafka·Postgres·관측 스택을 상시 클라우드에 올리면 월 비용이 크다.
- 선택지: A. 클라우드 상시 배포 / B. 로컬 실행 + README·화면 녹화·측정 결과.
- 결정: B.
- 이유: 이 프로젝트의 가치는 장애를 주입했을 때의 동작이고, 이는 재현 가능한 로컬 실험으로 보여 주는 편이 정확하다. `docker compose up` 한 번으로 누구나 재현하게 만든다.
- 포기한 것: 링크 하나로 바로 써 보는 경험. 화면 녹화로 대신한다.

## D4. 구조: 업무 경계로 나눈 MSA, 비동기는 Kafka, 동기는 서킷 브레이커 (2026-11-21)
- 상황: P1(외부 장애 전파)을 검증하려면 장애가 번지는 경로, 즉 서비스 사이 호출이 실제로 있어야 한다. 주인도 Kafka와 서킷 브레이커를 서비스 사이에서 써 보고 싶어 한다.
- 선택지: A. 모듈러 모놀리스(한 프로세스, 모듈 경계만) / B. 업무 경계 MSA, 서비스별 DB / C. A로 시작해 일부만 분리.
- 결정: B. 서비스 사이 비동기는 Kafka 이벤트(코레오그래피 Saga), 동기는 조회에만 쓰고 호출하는 쪽이 타임아웃·서킷 브레이커·대체 응답을 책임진다. 코드는 하나의 저장소(Gradle 멀티 모듈)에 둔다.
- 이유: 장애 격리, 이벤트 전달 보장, 서비스별 데이터 소유 같은 MSA의 어려운 부분이 곧 이 프로젝트의 검증 대상이다. 저장소를 하나로 두면 공통 규칙(Outbox, 멱등키, 이벤트 계약)을 한 번만 만들고 함께 테스트할 수 있다.
- 포기한 것: 모놀리스의 단순함과 한 트랜잭션 정합성. 서비스마다 "왜 나눴는가"를 설계 ADR에 남겨, 나눌 이유가 약하면 합친다.

## D5. 강조점: 커머스·플랫폼 회사 (2026-11-21)
- 상황: 주인이 가장 원하는 곳은 커머스·플랫폼 회사다.
- 결정: 광고·과금·정산 도메인 깊이와 대용량 이벤트 처리(노출 파이프라인, 부하 실험)를 앞세운다. 에이전트는 "운영 생산성 + 정합성" 관점으로 보여 준다.
- 포기한 것: 핀테크 전용 주제(PG 자체 구현, 금융 규제 대응)는 다루지 않는다.
